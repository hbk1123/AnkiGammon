# XG2Anki Filter Builder compatibility

Status: Draft v0.1  
Branch: `feature/xg2anki-filterbuilder-compat`  
Verified against public XG2Anki Filter Builder on 2026-09-29.

## 1. Goal

Make Anki cards generated by AnkiGammon searchable with the public XG2Anki Filter Builder where the required information can be derived from AnkiGammon's existing `Decision` data.

This is a compatibility layer, not a reimplementation of XG2Anki. AnkiGammon remains the source of truth for analysis data and rendering.

Primary user workflow:

1. Import/analyse positions with AnkiGammon.
2. Export or sync one large personal-error deck to Anki.
3. Use XG2Anki Filter Builder to generate Anki search queries.
4. Use those queries in Anki Browser or Filtered Decks for thematic study.

## 2. External references

- Upstream AnkiGammon: https://github.com/Deinonychus999/AnkiGammon
- Working fork: https://github.com/hbk1123/AnkiGammon
- XG2Anki: https://xg2anki.de/
- Filter Builder: https://fb.xg2anki.de/

The Filter Builder is not versioned in this repository. Compatibility requirements below are therefore frozen from the public HTML/JavaScript observed on 2026-09-29.

## 3. Current AnkiGammon note schema

Current Anki note fields:

```text
XGID
Front
Back
AnalysisData
```

Relevant current properties:

- `XGID` is already an independent searchable field.
- `AnalysisData` serializes the full `Decision` object.
- Existing-note upsert is keyed by XGID.
- Existing note-type migration can append missing fields through AnkiConnect.
- APKG GUID generation depends only on XGID, which must remain field index 0.
- `Decision.candidate_moves` contains candidate notation, rank, error, and `was_played`.
- Checker-play error data is available through `xg_error_move`, `Move.xg_error`, or `Move.error`.
- Cube/take error data is available through `cube_error` and `take_error`.
- Score, match length, Crawford state, cube state, dice, and win/gammon/backgammon percentages are already represented by `Decision`.

## 4. Compatibility already confirmed

The following Filter Builder features use `XGID:re:` and already work with AnkiGammon cards:

- Position Pattern
- checker-play-only / cube-action-only
- on-roll filters
- roll filters
- cube position filters
- unlimited/match filters based directly on XGID
- board-pattern combinations built from XGID

Manual testing on an AnkiGammon-generated deck confirmed that a specific prime structure can be extracted successfully.

The Filter Builder's "Initialisation of Filter Fields using an XGID" UI currently resets after briefly populating fields in the user's browser. This occurs even with an XGID copied directly from eXtreme Gammon and is therefore not an AnkiGammon compatibility requirement.

## 5. Phase 1 target

Phase 1 should unlock the highest-value filters without adding new engine analysis.

### 5.1 New hidden/searchable note fields

Append these fields after the existing fields:

```text
Multiple Choice List
Multiple Choice Answer
Best Action
Action Done
```

Do not reorder existing fields. In particular, `XGID` must remain field 0.

These fields are metadata for searching. They do not need to be referenced by the Anki card templates.

### 5.2 Multiple Choice List

Filter Builder Move Filters search this field directly.

Observed examples of generated filters include:

```text
"Multiple Choice List:re:(?-i).*\\).*/13.*"
"Multiple Choice List:re:(?-i)[^;]*\\*[^;]*\\*[^;]*;"
"Multiple Choice List:re:(?-i).*/18.*"
```

Required serialization shape:

```text
(a) MOVE1;(b) MOVE2;(c) MOVE3;...
```

Requirements:

- lower-case labels in parentheses: `(a)`, `(b)`, ...
- one space after the closing parenthesis
- semicolon between options
- preserve XG-style move notation
- preserve hit marker `*`
- deterministic output
- no HTML in this field

For checker play, derive options from the same candidate subset intended for the card/export, rather than inventing moves.

### 5.3 Best Action

For checker play, store the notation of the rank-1/best move.

The field must preserve `*` because Filter Builder uses it for hit-error filters.

Example:

```text
13/7* 6/5
```

### 5.4 Action Done

For checker play, store the notation of the move with `was_played == True`.

The field must preserve `*`.

This unlocks the checker-play Action Done filters:

```text
Missed Hits:
-"Action Done:*\\**" "Best Action:*\\**"

Wrong Hits:
"Action Done:*\\**" -"Best Action:*\\**"
```

If no played action is known, leave the field empty. Do not guess.

### 5.5 Multiple Choice Answer

Store the lower-case compatibility option letter corresponding to the best action, e.g. `a`.

This must be based on the compatibility list, not on any randomized visual order used by the rendered Anki card.

For Phase 1 checker-play Move Filters this field is not required, but adding it now avoids a second schema migration before cube-filter work.

## 6. Move Filters unlocked by Multiple Choice List + XGID

The current Filter Builder implementation constructs these from `Multiple Choice List` and, in many cases, `XGID`:

- Stack
- Stack & Up
- Pick & Pass
- Hit
- Double Hit
- Breaking the 18-point anchor
- Breaking the 20-point anchor
- Breaking the 21-point anchor
- Breaking the 22-point anchor
- Breaking the midpoint
- Making the 18-point anchor

Therefore the first implementation milestone is successful compatibility with these filters.

## 7. Compatibility tags

Tags should be generated separately from the existing basic AnkiGammon tags.

### 7.1 Error Size

Filter Builder searches buckets, not an `Error Size` field:

```text
X2A::ErrorSize::NoError
X2A::ErrorSize::000
X2A::ErrorSize::020
X2A::ErrorSize::050
X2A::ErrorSize::080
X2A::ErrorSize::100
X2A::ErrorSize::200
...
X2A::ErrorSize::900
```

Observed bucket definitions:

| Tag suffix | Equity loss |
|---|---:|
| NoError | 0 mp |
| 000 | 1-19 mp |
| 020 | 20-49 mp |
| 050 | 50-79 mp |
| 080 | 80-99 mp |
| 100 | 100-199 mp |
| 200 | 200-299 mp |
| 300 | 300-399 mp |
| 400 | 400-499 mp |
| 500 | 500-599 mp |
| 600 | 600-699 mp |
| 700 | 700-799 mp |
| 800 | 800-899 mp |
| 900 | 900+ mp |

Use authoritative XG error where available. Do not silently replace an unavailable error with zero.

### 7.2 Away-score tags

Filter Builder searches:

```text
X2A::Score::AwayPlayer::<NN>
X2A::Score::AwayOpponent::<NN>
```

with `01C` used for Crawford one-away.

These are derivable from match length and score, but the exact mapping of "Player" and "Opponent" must be tied to the card's bottom-player perspective, not assumed from X/O naming. Add tests before enabling these tags.

### 7.3 Position-feature tags

Filter Builder searches:

```text
X2A::PositionFeature::AnchorsMadeOpponent::<N>
X2A::PositionFeature::AnchorsMadePlayer::<N>
X2A::PositionFeature::BackCheckersOpponent::<N>
X2A::PositionFeature::BackCheckersPlayer::<N>
X2A::PositionFeature::HomePointsMadeOpponent::<N>
X2A::PositionFeature::HomePointsMadePlayer::<N>
X2A::PositionFeature::PointsMadeOpponent::<N>
X2A::PositionFeature::PointsMadePlayer::<N>
X2A::PositionFeature::CheckersOffOpponent::<N>
X2A::PositionFeature::CheckersOffPlayer::<N>
```

These are derivable from the board state and can be added after the Phase 1 field compatibility is proven.

## 8. Cube Action filters

Current Filter Builder cube-error queries depend on all of the following:

```text
Multiple Choice Answer
Action Done
X2A::ActionType::Cube::DN
X2A::ActionType::Cube::TP
```

Examples from the current Filter Builder:

```text
tag:X2A::ActionType::Cube::DN
("Multiple Choice Answer:c" or "Multiple Choice Answer:d")
("Action Done:No_*" or "Action Done:Too_*")
```

and:

```text
tag:X2A::ActionType::Cube::TP
("Multiple Choice Answer:b" or "Multiple Choice Answer:d")
"Action Done:_*Pass"
```

Do not implement these by guessing XG2Anki's Action Done vocabulary.

Before cube-personal-error compatibility is enabled, capture and document the exact XG2Anki strings used for:
- No Double
- Too Good
- Double
- Take
- Pass
- Beaver, if supported

AnkiGammon's split-cube-decision behavior also needs an explicit mapping to DN (doubling decision) versus TP (take/pass decision).

Cube compatibility is therefore Phase 2 unless exact string fixtures are obtained first.

## 9. Extra Info filters

The Filter Builder uses a field named:

```text
XG Results - Extra Info
```

for several percentage-based filters, including win, gammon and backgammon percentages.

AnkiGammon already stores these numerical values, so compatibility is technically possible, but the Filter Builder regex depends on a positional whitespace-delimited string format.

Do not add this field until that serialization format has been captured exactly and covered by fixture tests.

## 10. Score Matrix and advanced XG2Anki-only data

The current Filter Builder directly searches a `Score Matrix` HTML field, including `ShowScoreInfo(...)` fragments and action abbreviations such as `TG/P`, `D/P`, `D/T`, and `N/T`.

This is not Phase 1.

Also out of initial scope:

- Dirk's manual tags (`M::...`)
- `X2A::PositionType::...` where classification rules are not yet reproduced
- `X2A::BestMoveDistinctCount::...`
- `X2A::BestMoveDistinctCountNeutralScore::...`
- `X2A::Volatility::...`
- Score Matrix pattern compatibility

`X2A::SecondBest::...` may be derivable from existing candidate errors and can be evaluated separately.

## 11. Proposed architecture

Add a small, pure compatibility module rather than embedding XG2Anki rules into rendering code.

Suggested module:

```text
ankigammon/anki/xg2anki_compat.py
```

Suggested responsibilities:

```python
build_compat_fields(decision, candidate_limit) -> dict[str, str]
build_compat_tags(decision) -> list[str]
serialize_multiple_choice_list(moves) -> str
error_size_bucket(error) -> str | None
```

Rules:

- `AnalysisData` remains canonical.
- compatibility fields/tags are derived output.
- no compatibility data should alter engine analysis.
- no compatibility data should alter visual rendering.
- functions should be deterministic and unit-testable without Anki or Qt.

## 12. Integration points

### AnkiConnect

`ankigammon/anki/ankiconnect.py`

- append missing compatibility fields to an existing current or legacy note type
- include compatibility fields when adding a note
- include compatibility fields when updating a note
- preserve XGID-based upsert and review history
- adding fields to an old note type must not delete or rewrite unrelated user data

### APKG

`ankigammon/anki/apkg_exporter.py`

- append compatibility fields to the model after `AnalysisData`
- include compatibility field values in `StableNote.fields`
- keep XGID at index 0 so GUID behavior remains unchanged

### Card generation / export data

`ankigammon/anki/card_generator.py`

- expose compatibility metadata alongside `front`, `back`, `tags`, `xgid`, and `analysis_data`
- do not couple compatibility field generation to HTML rendering

### Tags

Keep one shared tag-generation path so direct Anki sync and APKG export do not diverge.

## 13. Existing-card migration

Schema migration and data backfill are separate concerns.

On first run after upgrade:

1. append any missing compatibility fields to the note type
2. do not fabricate values for old notes merely because fields now exist

When an existing XGID is re-exported/upserted from AnkiGammon:

- populate/update compatibility fields from the current `Decision`
- preserve the note/card identity and review history

A future optional bulk backfill may deserialize existing `AnalysisData`, but it is not required for the first implementation.

## 14. Acceptance tests

Phase 1 is not complete until all of these pass.

### Schema and migration

1. New model contains:
   - XGID
   - Front
   - Back
   - AnalysisData
   - Multiple Choice List
   - Multiple Choice Answer
   - Best Action
   - Action Done
2. Existing model gains only missing fields.
3. XGID remains the first APKG field.
4. Re-export of the same XGID does not create a duplicate note/card.
5. Existing review history is preserved on AnkiConnect upsert.

### Field serialization

6. Checker candidates serialize exactly as semicolon-delimited `(a) ...;(b) ...;` metadata.
7. Hit marker `*` survives serialization.
8. Best Action uses the best move notation.
9. Action Done uses the actual played move notation.
10. Unknown played action produces an empty Action Done field.
11. Compatibility Multiple Choice Answer is deterministic.

### Filter Builder integration

Use the public Filter Builder to generate the query, then run it against test cards in Anki.

12. Position Pattern still works.
13. Hit filter returns the expected fixture.
14. Double Hit filter returns the expected fixture.
15. At least one Stack/Stack & Up fixture works.
16. At least one anchor-breaking fixture works.
17. Missed Hit returns a card where Best Action contains `*` and Action Done does not.
18. Wrong Hit returns a card where Action Done contains `*` and Best Action does not.

### Regression

19. Front/back rendering is byte-equivalent or functionally unchanged apart from hidden metadata.
20. Study pack format remains valid.
21. Existing basic tags remain present.
22. Existing direct Anki sync and APKG export tests pass.

## 15. Implementation order for Codex

1. Add unit tests for compatibility serialization first.
2. Add `xg2anki_compat.py`.
3. Add the four Phase 1 fields to APKG model/export.
4. Add field migration and add/update support to AnkiConnect.
5. Add checker-play Best Action / Action Done.
6. Add ErrorSize tags.
7. Run existing test suite.
8. Build a small fixture deck.
9. Validate real queries copied from Filter Builder in Anki.
10. Only after that, expand to score/position-feature/cube compatibility.

## 16. Non-goals

Do not:

- clone or embed the XG2Anki Filter Builder
- depend on XG2Anki at runtime
- scrape XG2Anki during normal AnkiGammon operation
- change XG analysis results to fit XG2Anki
- replace `AnalysisData` with compatibility fields
- change XGID encoding
- change note GUID/upsert identity
- implement undocumented XG2Anki fields by guesswork
- attempt full XG2Anki field parity in the first PR

The desired result is a thin, testable search-compatibility layer.
